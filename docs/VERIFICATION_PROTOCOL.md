# Verification Protocol — як перевіряти правила з навчальних відео

Контекст: власник присилає transcript'и відео DoubleTop (витягнуті через
`youtube-transcript-api`). Текст без зображень — ризик неточностей. Цей
документ фіксує процедуру, якої дотримується Claude при інкорпорації
правил у MCP, щоб не додавати як "істину" те, що на наших даних не
підтверджується.

## Три рівні верифікації

### 1. Витягнення claim-ів (explicit, не концептів)

З transcript-а виділяти **твердження з числами** — вони перевірювані.
Концепти без чисел (визначення: "sweep", "deviation", "range") — лише
нотувати, не верифікувати.

Приклад (з лекції «Рейнджі», `kdEygb8UPKU`):

| Claim | Клас |
|---|---|
| "70% часу ринок у рейнджі" | кількісний → verify |
| "реакція від низу зазвичай 10-20%" | кількісний → verify |
| "виніс = 1 з 5-10 торкань краю" | кількісний → verify |
| "на bear-range працює верхня ліквідність" | напрямний → verify |
| "sweep = свічка з довгим фітилем, що проколює і закривається назад" | визначення → не verify |

### 2. Empirical test на наших даних

Для кожного кількісного claim-у знайти функцію з наших tools:

| Шаблон claim-у | Verification path |
|---|---|
| "X% часу у рейнджі" | `range_detect(1d, lookback_bars≥730)` → `sum(n_bars_in_ranges) / total` |
| "реакція N%" | `event_study(events=sweep_timestamps, measure='max_up' чи 'max_dd')` → порівняти p25/median/p75 з N |
| "N з M торкань край — виніс" | `detect_deviations` + свій class → ratio |
| "регіме A → патерн B" | фільтрувати `range_detect.sweeps` по `market_regime` → порахувати частку |

### 3. Verdict з явним маркером

- **✓ CONFIRMED** — число з лекції у межах довірчого інтервалу нашої вибірки (±10pp для процентів, ±1σ для z-score, etc.).
- **≈ DIRECTIONALLY RIGHT** — знак/напрям сходиться, числа розходяться. Вказати delta.
- **✗ NOT CONFIRMED** — пряма розбіжність на наших даних і thresholds.
- **◯ UNVERIFIABLE** — поточні tools цього claim-у не вимірюють.

Обов'язково вказати:
- `n_sample` і `period` (DoubleTop pattern).
- Thresholds, які використовував (напр., `max_width_pct=10%`).
- Caveats (один символ, один TF — на інших може бути інакше).

### 4. Якщо результат не збігся — хто винен?

Три можливості, у порядку ймовірності:
1. **Параметри нашого детектора** — я обрав thresholds навмання. Варіювати і подивитись.
2. **Горизонт вибірки** — 500 бар'ів 1h може не відображати довгострокову тезу.
3. **Timeframe** — denne vs годинне можуть дати різні цифри.

**Тільки якщо після усіх варіацій розбіжність лишається — тоді слабка підстава сумніватись у claim-і.** І навіть тоді — ввічливо, бо лектор може мати доступ до даних і pattern-ів, яких у нас немає.

## Приклад (виконано 2026-10-12 на лекції «Рейнджі»)

**Claim**: "70% часу ринок у рейнджі".

**Test**: `range_detect(venue='binanceusdm', symbol='BTC/USDT:USDT',
timeframe='1h', lookback_bars=500, min_bars=20, max_width_pct=10,
source='live')`.

**Result**: 500/500 bars in range (100%).

**Verdict**: ≈ DIRECTIONALLY RIGHT but off by 30pp.

**Diagnosis**: детектор з `max_width_pct=10%` і `min_bars=20` на 21-денному
горизонті засмоктує весь BTC-рух 2026-10 як один великий рейндж. Для
структурної перевірки потрібно: (a) 1d bars × ≥ 2 роки, (b) `max_width_pct`
~ 5-7%, (c) можливо правило "trending segment між рейнджами". Залишається
TODO для `range_detect` калібрування.

**Висновок**: претензія лекції не підтверджена **з поточними** параметрами
на вузькій вибірці. Напрямок (ринок переважно боковий) узгоджується з
нашим спостереженням, але конкретне число 70% з наших даних витягнути не
вийшло.

## Що робити, якщо claim unverifiable

Якщо жоден з існуючих tools не вимірює claim — записати як відкрите питання
у відповідному BACKLOG-пункті або створити новий. Наприклад:

> "lecture X claims N% of pattern Y have outcome Z — needs
> `event_study` extension to recognise Y-events; add as 1.XX in BACKLOG."

## Де фіксувати результат верифікації

Звіти з бектестами на історії — у `docs/verification/<дата>-<тема>.md` (перший: `2026-10-12-doubletop-ranges-sfp.md`, скрипт `scripts/verify_lectures.py`).

Кожна інкорпорація правила з лекції у MCP супроводжується `verify-note`
коміту з посиланням на цей документ, verdict'ами і параметрами. Приклад
живе у `CHANGELOG.md` → "Фаза 1.17" (там зафіксовано, що live BTC 4h
показав 3 high-sweeps підряд, тобто патерн bear-range знімає верхню
ліквідність — підтвердження claim-у з лекції).

## WebSearch як вторинне cross-джерело

Коли наш empirical test двозначний — можу запустити WebSearch на
research-пости (Delphi, Kaiko, Glassnode) для порівняння напрямку
висновку. **Не копіювати цифри одна-в-одну** (методології різні), тільки
порівнювати напрямок.
