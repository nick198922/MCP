- Колектор `trader_positions` (пункт 471 постійної картки, картка [hlp-inventory-crowding](../ideas/IDEA-20261026-hlp-inventory-crowding.md), тріаж п. 3): у кожному запуску, одразу після акаунтів Hyperliquid, опитує **батьківське HLP і всі його дочірні сховища** незалежно від рангу в лідерборді, кожне окремо (Strategy A, B, X, ліквідатори 1–4). Лише читання публічного API HL, без ключів і `execution/`.
  - Список — `vaultDetails` HLP через провайдер (`Hyperliquid.vault_children`, `parse_vault_children`; ліміт HL 5 запитів/с з `Runtime`, кеш 300 с). Адресу батька `0xdfc24b07…f303` підтверджено живою відповіддю 26.11 (`vaultAddress`, `relationship.type = parent`, 7 `childAddresses`). Відповідь недовірена: інша `vaultAddress` чи не «parent» — помилка; адреси не `0x` + 40 hex відкидаються, дублікати й сам батько — теж, не більше 20.
  - Батька опитуємо теж: один запит на запуск; 26.11 позицій у нього нема, але якщо HL поверне інвентар на батька (ризик «зміна архітектури сховищ» у картці), запис це побачить.
  - Збій `vaultDetails` — опитується список останнього запуску HLP (його маркери в `trader_polls`); нема й його — HLP цього запуску не опитується, решта працює. Збій одного сховища не зупиняє інших (маркер `ok = 0`). Будь-який інший збій частини HLP (напр. помилка запису в БД) лише пишеться в лог: завдання не падає, Polymarket опитується далі (правка після рев'ю, тест).
  - Обмеження: година ряду здоров'я зараховується, коли опитано хоч одне з 8 сховищ, тож тривалий збій лише Strategy A чи B у ньому не видно (рев'ю, зауваження 3).
