## Правки за [рев'ю підготовки](../reviews/2026-11-26-smart-money-slice2-prep.md) (request changes)
- Блокер 1. У картці, в пункті «Прогін зрізу 2», записано «Порядок спроб `--stage full`» (до даних зрізу 2). Вирішальна — перша спроба серії, що записала JSON з H3 без `stopped`, і всі гіпотези (H1, H1w, H2 з рішенням, H3) беруться лише з неї. Повтор дозволено лише після збою до JSON або після `stopped`. Повтор `--no-fetch` — не спроба. Пункт «Зріз 3» тепер посилається на JSON вирішальної спроби з sha256.
- Раннер, щоб правило трималося кодом:
  - `decisive_attempt`: `--stage full` на вирішальній даті відмовляє до читання бази, якщо в серії `--out` уже є JSON цієї дати з H3 без `stopped`;
  - `--no-fetch` на вирішальній даті вимагає `--out`;
  - `load_prior` не приймає JSON повтору `--no-fetch` (`fetch_failed` = null).
- Знахідка 3: `free_out` відхиляє `--out` без `.md`. Раніше він зациклювався на `rep`, а `x.json` писав текст туди, де має бути JSON.
- Знахідка 4: у картці записано, що `coverage` і `full` запускаються не раніше 2026-12-16 01:00 UTC, і що саме перевірити в `coverage.md`.
- Знахідка 6: `fetch` повертає лічильник `failed`, а JSON `full` пише його як описове `fetch_failed` (null для `--no-fetch`). Жодне рішення це поле не читає, `prior_from_body` і відбиток реєстрації його не бачать.
- Знахідку 2 (HL без повторів) не чіпали, як і вирішено. Її покриває п. 2 правила.
- Тести: `--out` без `.md`, `fetch_failed` (JSON приймається як prior, а повтор — ні), `decisive_attempt` (збій, `stopped`, повтор, інша дата, файл поза серією, числовий порядок `full.5` < `full.10`, старий `full.json` без ключа). Офлайн-повтор зрізу 1 новим кодом дав JSON, ідентичний `full.json` без `hl_zero_quality` і `fetch_failed`. Для зрізу 1 `decisive_attempt` повертає `full.json`, prior приймається для погляду 2.
