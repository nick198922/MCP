# Рев'ю: фільтр `tag` через json_each (пункт 396a)

Режим C. Вердикт: **approve**. Блокерів немає.

Перевірено сам: `make lint` чистий; `pytest` на tests/test_store.py, test_tool_descriptions_units.py, test_tool_failure_extra_19/20.py, test_journal.py, test_positions.py, test_trade_plan.py: 135 passed. Grep по `src/`: інших `tags LIKE` не лишилось, три місця викликають спільний `_TAG_MATCH`.

## Перевірка за пунктами

1. Коректність викликів. `journal_list`, `positions_list`, `plan_list` (`tag`) використовують `_TAG_MATCH`, `exclude_tag` іде через `NOT _TAG_MATCH`. Порядок параметрів збігається з порядком `?` у `where`, бо кожен предикат має один `?`. `journal_stats`, `plan_review`, `positions_risk` ідуть через ці самі функції, окремого SQL немає.
2. Ін'єкції. Тег лише біндиться (`?`), у SQL вставляється тільки константа `_TAG_MATCH`. Ок.
3. Старі рядки з `\u`-екранування: `json_each` декодує, тест на це є (`хедж` знаходить рядок 1, але не `хеджування`).
4. Регістр: `COLLATE NOCASE` лише ASCII, як і було; описи це кажуть правильно.
5. Невалідний JSON, NULL, `[NaN]`: читається як `[]`, запит не падає. Зміна поведінки задокументована в `docs/changes/` і в тесті.
6. Інваріанти CLAUDE.md: I/O лише в store, інструменти не кидають, описи англійською, одиниці не зачеплено. Нових інструментів немає.
7. Тести впали б на старому коді: кирилиця, `a_b`/`a%`, `хеджув`, невалідний JSON і `exclude_tag` перевіряються.

## Зауваження (не блокери)

1. Низька. Зміна поведінки `exclude_tag` на NULL у `tags`: раніше `NULL NOT LIKE ?` давало NULL, і рядок відсікався; тепер його повертають. Це правильніше (тіньові плани мають тег, плани без тегів не повинні зникати), але в нотатці `docs/changes/` про це не сказано. Додати один рядок.
2. Низька. Якщо `tags` це JSON-об'єкт, `json_each` перебирає його значення, і значення може збігтися з тегом. Коментар у коді каже «top-level element». Практично нереалістично (`json.dumps(list)`), документувати не обов'язково.
3. Низька. Опис `plan_list` каже «ASCII letters case-insensitive» без згадки кирилиці; для консистентності з двома іншими описами можна додати «non-ASCII exact».
