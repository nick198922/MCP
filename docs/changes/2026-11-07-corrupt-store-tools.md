# 2026-11-07 · Інструменти зі сховищем при зіпсованій і заблокованій БД (пункт 218)

Пункт 218 [постійної картки](../ideas/IDEA-20261102-standing-improvements.md), лишок BACKLOG 6.41 «збої БД не перевіряються». Додано лише тест `tests/test_tools_corrupt_store.py`; `src/`, `execution/`, колектори й реєстрації не чіпано.

- **Що перевіряється.** Усі 38 інструментів зі сховищем (той самий AST-скан, що в `tests/test_tools_no_store.py`) викликаються через MCP-клієнт у трьох режимах:
  - `random_bytes`: файл БД із 64 КБ випадкових байтів. `Store.init()` кидає `DatabaseError: file is not a database`;
  - `truncated`: валідна мігрована БД із рядком журналу, обрізана наполовину. `Store.init()` кидає `DatabaseError: database disk image is malformed`;
  - `locked`: відкрите сховище сервера, а інше з'єднання тримає `BEGIN EXCLUSIVE`. `busy_timeout` 50 мс, у продакшні 5 с. Перед блокуванням інструменти створюють рядки журналу, позиції, правила й плану, тож `*_close` / `rules_disable` / `plan_link` справді доходять до запису.
- **Результат: порушень 0, виправлено 0.** Жоден інструмент не кинув виняток, і кожен повернув конверт:
  - зіпсований і обрізаний файл: 36 з 38 інструментів повертають `ok=false` і `missing: store` (`backend_error`) через `tools._util.store_ready`. `range_setup` з тестовими аргументами читає живі бари; з `source='store'` він теж повертає `ok=false` (окремий тест). `system_health` сам сховище не відкриває і показує його як `not_initialised`;
  - заблокована БД: у режимі WAL читання працює (видно останні закомічені дані, `journal_list` повертає рядок). Дев'ять інструментів, що пишуть (`events_seed_load`, `journal_add`, `journal_close`, `plan_add`, `plan_link`, `positions_add`, `positions_close`, `rules_disable`, `rules_presets_load`), повертають `ok=false` і `missing: store` з `database is locked`. Інших помилок сховища немає. Після зняття блокування `journal_add` знову пише, тобто невдалі записи відкочено і транзакція не зависла.
- **Лишилося, не виправлено (поза межами пункту):**
  - якщо файл зіпсовано вже на старті, `Store.init()` у lifespan (`server.py`) кидає виняток, і MCP-з'єднання не встановлюється. Тоді недоступні всі інструменти, навіть ті, що працюють без БД (перевірено: `DatabaseError: file is not a database` на клієнті). Чи це правильна поведінка (гучна відмова й перезапуск systemd), чи сервер має стартувати без сховища, вирішує власник;
  - блокування, яке забороняє й читання (`PRAGMA locking_mode=EXCLUSIVE` в іншому процесі), не перевірялось: у нашому коді такого режиму немає. Збій запиту при читанні вже покриває `test_store_query_error_goes_to_missing`.
- Перевірка: `make lint` пройшов, `tests/test_tools_corrupt_store.py` разом із `tests/test_tools_no_store.py` дали 14 passed (новий файл: 5 тестів, ≈ 3 с без xdist). Повний набір не запускали (за завданням).
