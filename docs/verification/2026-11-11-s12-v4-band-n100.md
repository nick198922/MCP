# Смуга бази S12 v4 для n 100 (поріг «зняти» правила S12)

Дата: 2026-11-11. Картка: [IDEA-20261102-standing-improvements](../ideas/IDEA-20261102-standing-improvements.md), пункт 318, реєстрація «Попередня реєстрація — пункт 318». Джерело завдання: зауваження 2 [рев'ю пункту 315](../reviews/2026-11-11-s12-stop-rule-block.md), BACKLOG «перерахувати `r_band` бази v4 для n 100».

## Навіщо
Правило власника Q-20261109-1 (блок «S12: правило зняття» звіту контрольної точки): вхід v4 (v4 + v9) при n ≥ 100 і середньому R нижче нижньої межі ковзної смуги бази → «зняти». Поріг n 30 (−0.827) узято з бази, а для n 100 стояла оцінка звіту 09.11 «за масштабом √(30/100) ≈ −0.50R». Тепер це число пораховано на самій базі.

## Метод
- **Вибірка** — та, що дала `PASSPORTS["v4"]` ([модулі S12, 01.11](2026-11-01-s12-modules.md)): кеш рядків `~/.cache/tradedesk-agents/s12_modules/S12/rows`, маска «V OOS» зі `stage_report` `scripts/verify_s12_modules.py` (топ-100 попереднього дня, оборот ≥ $5M, guard R:R / стоп / score, ланцюг без перекриття угод однієї монети, вхід за закриттям свічки дотику, вхід ≥ 2025-03-01). R — на ризик угоди з комісіями й проковзуванням бектесту, не на капітал. Угоди впорядковано за часом входу.
- **Розрахунок** — `setup_passport.r_band(..., n, reps=10 000, seed=20261030)`: i.i.d. — 10 000 вибірок по n угод з поверненням; ковзна — середнє кожного вікна з n послідовних угод. Поріг = p5 ковзної смуги (як поріг n 30).
- **Скрипт** [`scripts/verify_s12_band_n100.py`](../../scripts/verify_s12_band_n100.py): лише локальний кеш, без мережі й БД; пік пам'яті 454 МБ.
- **Порядок.** Реєстрацію записано в картку до прогону, але в тому самому кроці (так поставив завдання координатор): метод повністю заданий розрахунком n 30, вільного параметра, який можна було б підібрати під результат, немає.

## Перевірка тієї самої вибірки
n 8829, середній R −0.009, як у звіті 01.11. Смуга n 30 відтворена до третього знака: i.i.d. −0.440 / −0.022 / +0.496, ковзна −0.827 / −0.092 / +1.095 (= `PASSPORTS["v4"]`).

## Що змінено
- `S12_DROP_FLOOR` у `src/tradedesk/analytics/checkpoint.py` = `V4_BAND_SLIDING_N100[0]` = −0.524 (константи `V4_BAND_IID_N100`, `V4_BAND_SLIDING_N100` у `s12_demo_audit.py` поряд із `PASSPORTS`). Поріг n 30 (−0.827) не змінено.
- Рядок S12 таблиці `DEMO` і таблиця [CHECKPOINT](../CHECKPOINT-2026-11-30.md) отримали смугу n 100 (там стояло «n 100 не пораховано … порахувати тим самим `r_band`»); тест звірки документа з кодом більше не має винятків.

## Застереження
- Поріг м'якший за старий на 0.024R: демо із середнім між −0.524 і −0.50 на 100 угодах тепер «тримати», а не «зняти». На вердикт зараз не впливає: вхід v4 має n 36 (11.11), до 100 далеко.
- Ковзна смуга з 8730 вікон, що сильно перекриваються: незалежних вікон по 100 лише ≈ 88, тож p5 сам має похибку порядку кількох сотих R.
- База — бектест з моделлю витрат, а не демо; виконання на демо гірше (звірка 09.11), і саме це правило має ловити.
- Демо v4 + v9 — одне правило входу, але n 100 на демо — це ≈ 1–2 місяці угод, а смуга бази — розподіл вікон за 18 місяців; режим ринку в демо-вікні може відрізнятися від середнього бази.
- Поріг перевіряється щодня на зростаючому n, як і n 30: це сигнал, а не тест із рівнем 5 %.

Статус пункту: зроблено; поріг пораховано з бази.
