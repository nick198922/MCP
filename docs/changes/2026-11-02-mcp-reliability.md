- Надійність MCP-інструментів (пункт 7 [standing-improvements](../ideas/IDEA-20261102-standing-improvements.md)), розбір — [`verification/2026-11-02-mcp-reliability.md`](../verification/2026-11-02-mcp-reliability.md). Журнал `tradedesk-mcp` з клону агентів не читається (`journalctl` заборонено), тож докази — `system_health` живого сервісу, 7-денна повнота колекторів і живі запити з сервера.
- Ретраї ccxt (`providers/exchanges.py`): `Exchanges._call` тепер повторює виклик один раз з паузою 0.4 с лише після таймауту, помилки з'єднання чи HTTP 5xx (`RequestTimeout`, звичайна `NetworkError`, `ExchangeNotAvailable` без коду 4xx у тексті); 4xx, які ccxt теж мапить на `ExchangeNotAvailable` (400/403/404/405/409/410/451: гео-блок, WAF, кривий параметр), ліміти (`RateLimitExceeded`, `DDoSProtection`), техобслуговування й nonce не повторюються. У health потрапляє лише остаточний результат, як у `Http`; кожен повтор пише `log.info` (`ccxt:okx fetch_ticker: retry 1 after RequestTimeout`). Кількість — `min(TRADEDESK_HTTP_RETRIES, 1)` (`0` вимикає). Усі виклики `Exchanges` — публічні читання, повтор безпечний; `execution/` не зачеплено. Причина: `ccxt:okx` — 2 таймаути з 23 викликів за 45 хв (`okx GET …/funding-rate?instId=ETH-USDT-SWAP`), тоді як `Http`-провайдери мають по два ретраї, а ccxt — жодного.
- Кеш 404 (`core/http.py`): відповідь 404 (`data_unavailable`) на кешований виклик (`ttl > 0`) зберігається на той самий TTL і повертається тією самою помилкою без запиту й без нового збою в health; інші збої, як і раніше, не кешуються. Причина: `ff_calendar_nextweek.json` віддає 404, доки ForexFactory не опублікує наступний тиждень, а знімок асистента кожні 10 хв питав його знову (5 збоїв з 8 викликів `forexfactory` за 45 хв). Живцем 02.11: три виклики `next_week` — один запит, один збій.
- Тести (`tests/test_core.py`, по одному на виправлення): 404 кешується на TTL і рахується один раз, без TTL не кешується, 500 не кешується; один ретрай ccxt після `RequestTimeout` (health `ok`, 0 збоїв), після двох збоїв — `network` і один збій у health, без ретраю для лімітів / техобслуговування / `BadSymbol` і для `ExchangeNotAvailable` з 403 / 451, з одним ретраєм (і рядком у лозі) для 502, `retries=0` вимикає. `tests/test_collector.py` перевіряє, що `system_health` віддає `last_failure` / `last_failure_ts`.
- Найчастіша причина за кількістю — збої WebSocket-ліквідацій Bybit і OKX (по 7 з 8 прогонів за перші 30 хв після рестарту) — без тексту помилки: його стирав наступний успішний прогін, а відтворення 360 с (09:04–09:10 UTC) завершилось чисто. Транспорт наосліп не міняли. Натомість планувальник (`collector/scheduler.py`) тепер тримає `last_failure` / `last_failure_ts`, які успіх не стирає, і `system_health` показує їх для кожної задачі колектора. Тест `tests/test_collector.py::test_scheduler_keeps_last_failure_after_a_success`.
