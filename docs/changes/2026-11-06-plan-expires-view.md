# Безпечний показ `expires` збереженого плану (пункт 186)

- Джерело: рев'ю `docs/reviews/2026-11-05-plan-add-ms-expires.md`, п. 4 (не блокувало).
- `tools/trade_plan.py`: новий `_expires_view`, ним `_view` показує горизонт плану (`plan_list`, `plan_link`; `plan_review` і `plan_resolve` на такому плані ще падають раніше — BACKLOG 6.49). Коли в сховищі лежить значення, яке не є придатними unix-секундами (рядок, мілісекунди чи інше число поза діапазоном дат, NaN, `bool`, байти), відповідь містить `expires=None` і `expires_raw` — сире значення текстом, обрізане до 64 символів. Раніше рядок у `expires_ts` кидав `TypeError` із `_iso`, і `plan_list` падав замість конверта (інваріант 1); мілісекунди показувалися сирим числом у полі дати.
- Для нормальних планів відповідь не змінилась: `expires` — ISO-8601 UTC, поля `expires_raw` немає. Валідацію `plan_add`, `_iso` і логіку розрахунків (`review_open`, `analytics/trade_plan.py`) не чіпали; через `plan_add` таке значення й надалі не потрапляє в базу.
- Тести (`tests/test_trade_plan.py`): `test_plan_view_shows_a_stored_raw_expires_safely` — три плани через `plan_add`, двом у базі прямим `UPDATE` записано `"next friday"` і `1800000000000`; `plan_list` повертає `ok=true`, `expires=None` з `expires_raw` для них і ISO-дату без `expires_raw` для третього. На старому коді тест падав (`TypeError: 'str' object cannot be interpreted as an integer` → `Error executing tool plan_list`). `test_expires_view_never_raises` — NaN, `1e300`, `True`, байти, довгий рядок.
- Перевірка: `make lint`; `tests/test_trade_plan.py` + `tests/test_server.py` — 97 passed.
