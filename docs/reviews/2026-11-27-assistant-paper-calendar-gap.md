### 1. Неповний ланцюжок із виставленою експірацією 28–56 днів записується як пауза й закриває день (середня; імовірність мала, наслідок — хибний запис)

`prepare_chain` (`src/tradedesk/tools/assistant_paper.py:182-195`) шукає розрив у `by = group_by_expiry(build_chain(book, now))`. А `build_chain` (`src/tradedesk/analytics/options.py:120-122`) мовчки відкидає рядки без числового `underlying_price`. Якщо такими є всі рядки експірації в смузі, вона зникає з `by`, і виходить «є ближчі й дальші, всередині нічого».

Відтворено на фейкових рядках (`/home/tradedesk/.cache/tradedesk-agents/critic-498/probe_gap.py`, `NOW` = 10.10, 27NOV26 у смузі):

```
in-band expiry listed, underlying_price null on all its rows: ctx=None gap={'below': '30OCT26', ..., 'above': '26MAR27', ...}
in-band expiry listed, underlying_price is a string:          ctx=None gap={'below': '30OCT26', ..., 'above': '26MAR27', ...}
```

Наслідки:

- До зміни це була помилка з щогодинним повтором. Тепер це стан `skipped` без помилки в `system_health`, і повторів того дня немає.
- Бриф пише «немає експірації 28–56 днів», звіт чекпоінта — «це не збій», `reason` — «no listed expiry». Усі три твердження тоді хибні.
- Пункт 498 прямо вимагає: неповний ланцюжок лишається помилкою з повтором. Зараз «неповний» покрито лише випадком «експірації з одного боку».

Правка: судити про розрив за виставленими назвами, а не за відфільтрованими рядками. Наприклад, у гілці `if gap is not None`:

```python
listed = {p.expiry for s in book if (p := parse_option_name(str(s.get("instrument_name", ""))))}
if not any(band[0] <= (e - now).total_seconds() / 86400 <= band[1] for e in listed):
    ...  # наявна перевірка lo / hi і gap.update
```

Тест: додати в `test_job_calendar_gap_first_run_and_incomplete_chains` випадок «повний ланцюжок, але в усіх рядків 27NOV26 `underlying_price` = null» → `RuntimeError`, файлу стану немає. Без правки він має падати. Речення в `docs/changes` і докстрінг доповнити.
