Постійна картка `IDEA-20261102-standing-improvements`, п. 86. Переглянуто всі `docs/reviews/2026-11-05-*` з approve, зокрема ті, де зауваження сформульовано інакше, ніж «не блокує / nit / пізніше». Те, що вже розібрали [0405](2026-11-05-review-nits-0405.md) і [друге коло](2026-11-05-deferred-review-nits-2.md), не повторював. Кожне зауваження звірено з кодом. Реєстрації, критерії, колектори, `execution/` і заморожені форварди не зачеплено. Заборона підглядання Polymarket діє.

## Виправлено (з тестом)

- **`stage0_condor_forward.py` більше не перебудовує й не затирає `snapshots_v2.json`** ([рев'ю](../reviews/2026-11-05-stage0-condor-empty-cache.md), перше зауваження). `verify_put_skew.load_snapshots` перебудовує й перезаписує збережені поверхні, якщо `n_files` у файлі не збігається з кількістю файлів у `trades24/`. Якщо `trades24/` зник, перебудова виходить порожньою: 2112 поверхонь затираються, а звіт стадії 0 падає з traceback на `loaded 0 surfaces`. Я відтворив це на синтетичному кеші з вимкненою перевіркою. Якщо в `trades24/` з'явився новий файл, вхід стадії 0 мовчки змінюється. Тепер скрипт до `vom.load` порівнює ці два числа (рахує так само, як `load_snapshots`, файли `.part` не враховує). Якщо вони різні, виходить з кодом 1 і одним рядком: «snapshots_v2.json is stale (n_files …, trades24 has …); rebuild it with verify_put_skew.py». Тепер коментар «cache is read only here» відповідає дійсності. Тест `test_stage0_condor_forward_stale_snapshots_are_refused_not_rebuilt` перевіряє два випадки (`trades24/` немає при `n_files 3`; один новий файл при `n_files 0`). В обох: код 1, порожній stdout, точний рядок stderr, звіт не створено, кеш не змінився жодним байтом. З вимкненою перевіркою тест падає. На справжньому кеші сервера (05.11): `n_files 2112` і 2112 файлів, звіт будується як раніше (2112 поверхонь, ті самі рядки SD / MDE).
