- Дрібниці надійності після пункту 7 (пункт 8 [standing-improvements](../ideas/IDEA-20261102-standing-improvements.md), рев'ю [mcp-reliability](../reviews/2026-11-02-mcp-reliability.md), п. 3 і 6).
- Telegram `sendMessage` без дублів (`alerts/channels.py`, `core/http.py`): клієнт алертів створюється з `retry_unsent_only=True` і повторює запит лише тоді, коли Telegram його точно не отримав: помилка з'єднання / DNS / TLS (`ConnectError`, `ConnectTimeout`, `PoolTimeout`) або HTTP 429 (пауза з `retry_after` у тілі відповіді, максимум 5 с). Таймаут читання, обірване з'єднання і 5xx після відправки не повторюються: повідомлення могло вже дійти, а дубль ніде не видно; втрачений алерт видно в таблиці `alerts` як невдалий. Решта провайдерів `Http` поводиться як раніше (лише 429 тепер бере `retry_after` і з тіла, якщо нема заголовка).
- Пауза перед ретраєм — налаштування `Settings.http_retry_backoff` (0.4 с, як і було; з оточення не читається), `Runtime` передає її в усі `Http` і в `Exchanges`. Тестовий `Runtime` з `conftest` ставить 0. Джитер `Http` тепер пропорційний паузі (0.1 с при 0.4, тобто без змін у проді).
- Тести: `tests/test_alerts.py::test_telegram_send_message_retries_only_when_the_request_surely_did_not_arrive` (6 випадків: з'єднання / пул / 429 повторюються, таймаут читання / обрив / 502 ні), `tests/test_core.py::test_runtime_wires_http_retries_from_the_environment` (`TRADEDESK_HTTP_RETRIES` = 0 / 1 / 3 → кількість запитів `Http` і ccxt), `tests/test_core.py::test_runtime_retry_backoff_is_injectable_and_defaults_to_0_4_s`.
