# 2026-11-07 · Найповільніші тести, другий прохід (пункт 217)

Пункт 217 [постійної картки](../ideas/IDEA-20261102-standing-improvements.md). Перший прохід того ж дня: [пункт 190](2026-11-07-slow-tests.md) (файл з такою назвою вже був, тому цей має суфікс `-2`). Змінено лише `tests/test_tools_wrong_type_fields.py`; `src/`, `execution/` і колектори не чіпано, асерти й кількість мутацій ті самі.

- **Замір до змін.** `uv run pytest -q -n auto --durations=15`: 6962 passed, 3 skipped за 253 с. З них 151 с припадає на `test_s3_known_result_in_sample`, який має позначку `slow`, і `make test` його не запускає. У наборі `make test` (`-m "not slow"`) 6961 passed за 117–126 с, 578 с сумарного часу тестів, 73 тести довші за 2 с. Найдорожчі файли: `test_setup_signals` (108 с), `test_tools_wrong_type_fields` (86 с).
- **Причина в `test_tools_wrong_type_fields`.** Тест тут сам робив зайву роботу:
  - кожен свіжий runtime (до 13 на інструмент у тесті холодного кешу) мігрував нову SQLite-базу (≈ 0.14 с) і засівав її;
  - кожна мутація глибоко копіювала HTTP-тіло, хоча воно щойно розібране `json.loads`, і обходила все тіло з `float()` на кожному листку, щоб знайти одне поле.
- **Що змінено:**
  - засіяна база будується раз на модуль (фікстура `seeded_db`), і кожен runtime отримує власну копію файлу, тобто ті самі рядки й ту саму схему;
  - `numeric_fields(..., only=поле)` пропускає піддерева, чия назва не є префіксом поля. Результат той самий, це перевіряє новий асерт у `test_numeric_fields_and_break_field`;
  - HTTP-тіло ламається на місці. Результати ccxt, як і раніше, копіюються.
- **До / після** (той самий файл; «до» — версія з HEAD, запущена з копії `tests/`):
  - `-p no:xdist`: 95.6 → 48.7 с;
  - `-n 6`: 25.8 → 18.1 с (стіна), 89.8 → 54.1 с сумарно;
  - тестів довших за 2 с: 7 → 2. `deribit_vrp` 5.1 → 3.9 с і `cycle_regime` 3.4 → 3.2 с лишились, бо час іде на сам інструмент у `src/` (42–84 виклики, `vrp_summary` / режим циклу);
  - холодний кеш: `funding_spread_scan` 3.1 → 1.3 с, `test_the_cold_check_reaches_both_caches` 4.1 → 1.6 с.
- **Не змінено, причина поза тестом або в самій перевірці:**
  - `test_setup_signals` (25 тестів по 3–6.5 с): 99 % часу забирає скан `analytics/setup_signals` на кожному префіксі. Скоротити можна лише в `src/` або меншою вибіркою префіксів, а це послабило б перевірку (BACKLOG 6.37);
  - `test_carry_paper_engine`: повний прогін рушія вже робиться раз на процес;
  - `test_tools_malformed_200` / `never_raise` / `envelope_shape` / `bad_input`: один сервер на тест і ≈ 90 інструментів, нічого не будується повторно;
  - сканери `ast` (`test_naive_datetime`, `test_deps_check`, `test_store`): більшу частину часу забирає розбір ≈ 6 МБ коду. Швидший обхід дерева заощадив би лише ≈ 0.6 с;
  - реальних пауз у тестах немає (найбільша — навмисна `sleep(0.05)` у `test_store`).
- Повний набір повторно не запускали (за завданням): `make lint` пройшов, змінений файл — 182 passed.
